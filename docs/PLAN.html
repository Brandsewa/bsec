Implementation plan · rebuild from scratch

Bs Commerce multi-tenant platform

One modular-monolith platform that runs many independent Indian D2C stores on shared infrastructure. Each store has its own domain, theme, catalog, staff and customers. A store is a row of data; it is never a new server or app.

Version 2.0 · 28 Sep 2026 (audit changes applied)Starting infra 2 vCPU / 8 GB VPS, Ubuntu 24.04, CoolifyTeam assumption 1–2 developers with AI assistanceDelivery 10 milestones (M0–M9), exit criteria not dates

1. Goals and scope

Guiding rule: make one real store's commerce loop production-ready first (domain → product → cart → checkout → Razorpay/COD → order → stock → Shiprocket → invoice → notification → return/refund), migrate Bs Ecommerce onto it, then turn the proven engine into a self-service SaaS.

V0 · Internal platform (M0–M6)

  • Tenancy, staff logins and roles
  • Catalog, variants, categories, collections, inventory, media
  • Theme tokens, branding, home page sections, menus, pages
  • Storefront, cart, checkout, guest checkout
  • Razorpay, COD, orders, Shiprocket, GST invoices, returns, email
  • Customer accounts (OTP login, orders, addresses, wishlist)
  • Store status modes, indexing switch, basic SEO
  • Store #1 (Bs Ecommerce) live on the new platform

V1 · SaaS launch (M7–M9)

  • Self-signup one-pager, trial, templates
  • Custom domains (Cloudflare for SaaS)
  • Merchant billing, plans, size tiers, quotas
  • Super Admin: tenants, domains, usage, audit, support sessions, exports, per-store feature flags
  • Load, noisy-neighbour and concurrency tests passed

Deferred to V1.5 or later

  • Full app library (catalog, versions, rollouts, installs). V1 uses per-store feature flags instead (6.2).
  • Puck visual editor, WhatsApp, SMS, AI tools
  • Finance ledger, Razorpay Route settlements, POS, multi-warehouse transfers, B2B quotes
  • Advanced SEO: SEO score, Search Console / Bing integration, IndexNow, llms.txt
  • Advanced analytics, Expo mobile apps, Typesense, Valkey, separate API container for storefront traffic

Ideas borrowed as layout and feature references from Storify v2.3 (no code copied): split settings pages, the Online Store section, theme token editor with live preview, one-time token links, abandoned-cart recovery, search analytics, stock history. Gaps in the current Bs Ecommerce admin that this plan closes: no roles, placeholder theme page, no inventory ledger, no collections table, demo-data fallbacks.

Rules the code enforces

  • Route handlers never touch the database. They call domain services, which take a ctx: TenantContext as their first argument.
  • A lint rule bans importing db outside packages/db and packages/domain. All tenant queries run inside withTenant(ctx, tx => …).
  • Domain services emit events by enqueuing pg-boss jobs on the same transaction. Side effects (email, search, analytics) only happen in the worker.
  • Every write endpoint that a client may retry accepts an Idempotency-Key.

4. Tenancy and security model

Request flow

Host header ─► tenant resolver (cached host→tenant map, 60s + tag revalidation)
          ─► TenantContext { tenantId, storeStatus, actor, roles, requestId }
          ─► authorization (permission check per procedure)
          ─► domain service ─► withTenant(): BEGIN; SET LOCAL app.tenant_id = $1; … COMMIT
          ─► Postgres RLS policy: tenant_id = current_setting('app.tenant_id')::uuid

RLS pattern (applied to every tenant table)

ALTER TABLE products ENABLE ROW LEVEL SECURITY;
ALTER TABLE products FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON products
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
-- nullif is required: after a SET LOCAL transaction ends, the setting reads back as ''
-- on the same pooled connection, and ''::uuid raises an error (verified on PG 18.6).
-- app connects as role app_rw (not table owner). Migrations run as app_owner.
-- app_platform (BYPASSRLS) is used ONLY by the separate platform container, never by
-- the storefront/store API process. It exposes named functions, not arbitrary queries:
--   platformSuspendTenant() · platformRestoreTenant() · platformExportTenant()
--   platformDeleteTenant() · platformStartSupportSession() · platformUsageRollup()
-- Every call writes platform_audit_logs.

Identity model

  • Staff identity (merchants, their staff, platform team): one global users table. A person can belong to several stores through memberships. organizations group stores owned by one business; organization ≠ tenant.
  • Customer identity: customers are per store. The same email can register separately at two stores. Separate Better Auth instance and cookie (__Host-cust) scoped to the store's host.
  • Platform roles live in platform_staff, never inferred from a store role.

Security checklist

  • Verified on PostgreSQL 18.6: without FORCE ROW LEVEL SECURITY the table owner reads every store's rows; with it, 0 rows. App role cannot insert rows for another store. BYPASSRLS reads everything, which is why it is isolated in its own container.
  • Tenant never taken from the client; always from host (storefront) or session membership + X-Store-Id checked against memberships (admin).
  • Secrets (payment keys, shipping tokens) in tenant_secrets, encrypted with AES-256-GCM using a key from env; never returned to the browser after save.
  • Block JSON validated against the registry schema on save and render. No HTML except sanitized rich text.
  • Uploads: presigned R2 PUT, mime + size checks, per-plan storage quota, image re-encode through Cloudflare Images.
  • Rate limits by IP and tenant at Cloudflare and in Postgres (login, OTP, checkout, search).
  • Audit log for all privileged and platform actions; PII minimized in logs.
  • Cookies: Secure, HttpOnly, SameSite=Lax; CSRF protection on mutations; CSP on storefront.

5. Database schema

Conventions. Every table has id uuid pk default uuidv7(), created_at, updated_at timestamptz. Tables marked T have tenant_id uuid not null → tenants, RLS on, and indexes that start with tenant_id. Unique keys are per tenant, e.g. unique(tenant_id, slug). Foreign keys between tenant tables are composite (tenant_id, x_id) so a row can never point into another store. Money is bigint in paise with a currency char(3). Soft delete via deleted_at where noted.

6.3 Impersonation (support mode)

  • Started from Super Admin → Tenant → "Open as support", with a required reason and ticket reference.
  • Consent: the owner approves from an email or admin prompt, or the store has turned on standing consent in Settings, or a platform_owner starts an emergency session, which alerts the store owner immediately.

  • Implemented as a separate short-lived session carrying support_session_id, never by signing in as the merchant's own account.

11.2 Numbering

Order, invoice (per financial year), credit note and return numbers come from number_sequences with a single UPDATE … SET next_value = next_value + 1 … RETURNING inside the order or invoice transaction. Tested on PG 18.6 with 20 parallel clients: 1,000 orders, 1,000 unique numbers, no gaps.

11.3 Inventory reservation

UPDATE inventory_levels
   SET reserved = reserved + $qty
 WHERE tenant_id = $t AND variant_id = $v AND location_id = $l
   AND on_hand - reserved >= $qty
RETURNING id;          -- 0 rows = out of stock, abort checkout
INSERT INTO inventory_reservations (…, status 'active', expires_at now()+30 min);

Tested: 500 concurrent attempts against stock of 100 produced exactly 100 reservations and never oversold. On payment: reservation → committed, on_hand and reserved both decrease, movement row sold. Expiry job releases active reservations past expires_at; release is idempotent (only active rows change).

Razorpay, Shiprocket, Resend, Cloudflare API and (later) Typesense each have a platform kill switch flag and a fallback: Razorpay off → checkout offers COD only with a notice; Shiprocket off → manual fulfillment with tracking entry; Resend off → emails queue and retry; Typesense off → Postgres search. Failures show in Super Admin → System and never take down unrelated store functions.

Push-back and adjustments

  • It is not an installable package. Supabase's ui and ui-patterns live inside their monorepo. We port (copy and adapt) the pieces we need into packages/ui, keep the Apache-2.0 notice, and own them from then on. No upstream updates.
  • Do not copy the Supabase brand. Use the token system and patterns, but our own primary hue, logo, icons (Lucide) and fonts. The admin should feel Supabase-grade, not look like a Supabase clone.
  • Their code imports Next.js (next/link). Our admin is Vite + TanStack Router, so links and navigation helpers are swapped during the port.
  • It is built for developers on desktop, dark-first and dense. Our users are shop owners, often on a phone. We raise touch targets to 40 px on mobile, default to light theme, turn tables into card lists below 768 px, and use shop vocabulary ("Orders to ship", not "Pending fulfillment records").
  • Their Studio-specific pieces (SQL editor, logs charts, connect interstitials, assistant chat) are skipped.

Where skeletons are the wrong tool (we use something else):

  • Button actions and saves: button spinner + disabled state, then a toast.
  • Pagination, sorting, filtering a table that already has data: keep the old rows visible (placeholderData: keepPreviousData) with a thin progress bar, instead of blanking to a skeleton.
  • Data already in the query cache: render it immediately and refresh in the background.
  • Skeletons respect prefers-reduced-motion (no shimmer, static fill) and are hidden from screen readers, with aria-busy on the region.

Backups and disaster recovery

  • Targets: RPO ≤ 15 minutes (continuous WAL archiving to R2 with archive_timeout = 60s), RTO ≤ 2 hours (restore to a fresh VPS from runbook).
  • pgBackRest full weekly, differential daily, 30-day retention; R2 versioning on media; Coolify config, env templates, migration state and image tags backed up with each release.
  • A backup counts as valid only after a restore test. Monthly drill on staging, results logged in Super Admin → System.

Database migration safety

Expand → migrate → contract: add the new column or table, deploy code that works with both, backfill, switch reads, switch writes, remove the old schema in a later release. No destructive change while an older app version may still be running.
